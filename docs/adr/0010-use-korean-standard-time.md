# 0010. 서비스 시간 기준으로 한국 시간대 사용

## 상태

승인됨

## 배경

서비스의 현재 대상 사용자는 한국 시간대를 기준으로 활동한다. 체중 측정 시각, 생성일시, 수정일시처럼 사람이 입력하거나 확인하는 시각을 UTC로 저장한 뒤 변환하면, 초기 개발 단계에서는 불필요한 복잡도와 로컬, CI, DB 간 시간대 불일치 가능성이 생긴다.

## 결정

- 서비스의 날짜와 시간 기준은 `Asia/Seoul`로 통일한다.
- 날짜만 표현하는 값은 `LocalDate`와 `yyyy-MM-dd` 형식을 사용한다.
- 시각을 표현하는 값은 소수 초를 허용하는 ISO-8601 `LocalDateTime` 형식을 사용한다.
- 애플리케이션 시작 시 기본 JVM 시간대를 `Asia/Seoul`로 설정해 `java -jar`, IDE 직접 실행 등 실행 방식과 무관하게 정책을 적용한다.
- 애플리케이션 JVM과 CI JVM은 `Asia/Seoul` 기준으로 실행하고, H2 테스트 DB는 동일한 한국 표준시 오프셋인 `TIME ZONE=+09:00`으로 설정한다.
- MySQL을 도입할 때 서버와 연결 세션을 `Asia/Seoul` 또는 동일한 `+09:00`으로 설정한다.
- 신규 MySQL 시각 컬럼은 `DATETIME(6)`을 사용한다.
- 이미 적용된 Flyway 마이그레이션의 `TIMESTAMP(6)` 컬럼은 수정하지 않는다. 실제 MySQL 도입 시 전환이 필요하면 별도 버전 마이그레이션으로 처리한다.

## 결과

- 한국 시간대만을 대상으로 하는 현재 서비스에서 날짜와 시간의 의미를 단순하게 유지한다.
- 로컬, H2 테스트, CI, 패키징된 애플리케이션이 서로 다른 기본 시간대로 실행되는 문제를 자동 검증으로 방지한다.
- 해외 사용자, 다중 리전 운영, 시간대별 예약 기능이 필요한 시점에는 UTC 저장과 시간대 변환 전략을 다시 검토해야 한다.

## 검토한 대안

- UTC로 저장하고 API 경계에서 한국 시간대로 변환:
  - 이유: 다중 시간대 서비스에는 적합하지만, 현재 서비스 범위에서는 변환 규칙과 운영 복잡도가 이점보다 크므로 채택하지 않는다.
- 운영체제 시간대만 한국 시간대로 설정:
  - 이유: 로컬, CI, 컨테이너, DB 연결 세션의 기본값이 달라질 수 있어 일관성을 보장하지 못하므로 채택하지 않는다.
